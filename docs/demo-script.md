# 発表デモ台本（所要 3〜5 分）

題材は `samples/clinic_results_api`（ひかり診療所 検査結果API）。本物の AI は呼ばず、台本どおりに返す。各応答は2〜4秒（ランダム）。待っている間に次のセリフを話す。

## 起動

```sh
bun run demo
```

ブラウザで http://127.0.0.1:3000 を開く。データは `data/demo/` に作られ、普段のデータには触れない。やり直すときは `data/demo/` を消して起動し直す。

## 流れ

| # | 画面操作 | 話すセリフ |
|---|---|---|
| 1 | 一覧から `clinic_results_api` を選び、背景を確認して登録 → 分析を開始 | 「検査結果を患者アプリに返す診療所のAPIです。患者さんから『自分の ID ではない結果が出た』と問い合わせが来ています。コードを渡すと、運用中に起きる出来事を台本にしてくれます」 |
| 2 | 分析が終わるのを待つ（数秒）。構成図と出来事（12日目・45日目・90日目の3件）を見せる | 「3つの出来事が並びました。①他人の結果が見える ②任意ファイルを取れる ③管理用の一覧が認証なし。まず一番早い12日目から対応します」 |
| 3 | 12日目の出来事を開く。ログと左のコードを見せる | 「ログを見ると、同じキーで患者IDだけが次々変わっています。いきなり答えは出ません。先輩と会話して、自分で原因を突き止めます」 |
| 4 | 会話欄で **Enter（セリフが入る）→ Enter（送信）**。下の「会話」参照 | 入力されたセリフをそのまま読む |
| 5 | 会話が進み、方針（ready）が出たら「確認」ボタンで反映 | 「自分で決めた方針だけが、コードに反映されます」 |
| 6 | 「修正」タブで差分（app.py の変更）と自動チェックを見せる | 「SQLが `?` に変わり、本人確認が入りました。再スキャンで指摘が消えたことも確かめています」 |
| 7 | 会話に戻り、振り返りを続ける（Enter を4回） | 「直して終わりではなく、入れたあとのことと、次に活かすことまで考えます」 |
| 8 | 最後に学びがメモに残ることを見せる | 「この学びは次のアプリを作るときに呼び出されます。以上です」 |

## 会話（12日目「他人の検査結果が表示された」）

空の入力欄で Enter を押すと、次のセリフが入る（送信されない）。もう一度 Enter で送信。合計 6 セリフ = Enter 12 回。

| 回 | Enter で入る若手のセリフ | 返ってくる返事 |
|---|---|---|
| 0 | URLの患者IDを書き換えるだけで、他の人の検査結果が見られてしまっていると思います。 | 先輩「ログの患者IDは毎回違うね。app.py の44行目、APIキーで確かめているのは何だろう？」 |
| 1 | 認証が共通のAPIキーだけで、誰の結果かを確かめていません。しかもIDがSQLにそのまま入っているので、患者さんの個人情報が外から読み出されます。 | 医事課 担当「本当に他の患者さんの結果が見えているなら、すぐ止めたいです。ただ、アプリは診療時間中ずっと使われていて、止めると予約患者への連絡に影響します。」 / 先輩「原因と、誰に何が起きるかはつかめてるね。じゃあ、どう対応する？」 |
| 2 | 患者ごとのトークンで本人確認して、SQLはプレースホルダに直します。来月から3診療所が使うので、先に直します。 | 先輩「その方針で直してみようか。下の確認を押せば反映するよ。」（確認ボタンが出る → 手順5） |
| 3 | 患者向けアプリも、トークンを付けて呼ぶように直してもらいます。医事課にも連絡します。 | 先輩「連絡は大事だね。入れ替えるとき、古いやり方のままのアプリが残っていたらどうなる？」 |
| 4 | トークンを持っていない患者さんが見られなくならないか、診療時間外に確認してから入れ替えます。 | 先輩「その確認があれば安心だね。最後に、次にアプリを作るとき、最初から気をつけたいことは？」 |
| 5 | 次は、患者の情報を返すAPIは、最初から「誰が誰の分を見ていいか」を確かめる作りにします。 | 先輩「それを最初に決めておけば、今回の件は防げたね。お疲れさま。」（学びとして保存） |

- 回 2 の送信後に「確認」ボタンを押す。反映直後、先輩が「入れたよ。…入れ替えるとき、何を気にする？」と振り返りを始める。
- 迷ったら「ヒント」を押す。先輩が手がかりを3つ返す（Enter は使わない）。
- 回 3 以降は反映後に入力する。

## 振り返りパート（手順7〜8の詳しい台本）

「確認」で反映すると、先輩が先に話しかけてくる。

> 先輩「入れたよ。他の人のIDでは見えなくなって、SQLの穴もふさがった。ただ、患者向けアプリ側はまだ共通キーで呼んでるよね。入れ替えるとき、何を気にする？」

**発表者**：「直して終わり、ではありません。実際の運用では、入れたあとに何が起きるかまで考える必要があります。」

| 操作 | 画面に出るやりとり | 発表者のセリフ（返事を待つ間に） |
|---|---|---|
| Enter → Enter（回3） | 若手「患者向けアプリも、トークンを付けて呼ぶように直してもらいます。医事課にも連絡します。」<br>先輩「連絡は大事だね。入れ替えるとき、古いやり方のままのアプリが残っていたらどうなる？」 | 「APIだけ直しても、使う側が古いままだと患者さんが結果を見られなくなります。」 |
| Enter → Enter（回4） | 若手「トークンを持っていない患者さんが見られなくならないか、診療時間外に確認してから入れ替えます。」<br>先輩「その確認があれば安心だね。最後に、次にアプリを作るとき、最初から気をつけたいことは？」 | 「背景に書いた『診療時間中は止められない』という制約を踏まえて、入れ替えの段取りまで考えます。」 |
| Enter → Enter（回5） | 若手「次は、患者の情報を返すAPIは、最初から『誰が誰の分を見ていいか』を確かめる作りにします。」<br>先輩「それを最初に決めておけば、今回の件は防げたね。お疲れさま。」 | 「最後に、次に活かす学びを自分の言葉でまとめます。」 |

会話が終わると、回5のセリフが学びとして保存される。画面上部のメニュー「判断の記録」を開いて見せる。

**締めのセリフ**：「この学びは、次に別のアプリを見るときに関係する出来事と一緒に呼び出されます。見つけて直すだけでなく、判断の経験を積み重ねていけるのが Judgineer です。ありがとうございました。」

## 他の出来事を見せたいとき（任意・時間があれば）

- 45日目（任意ファイルのダウンロード）、90日目（認証なしの export）も開ける。Enter で入るセリフは1つ目の出来事用なので、自分の言葉で話してよい。方針を言えば ready に進み、反映できる。
