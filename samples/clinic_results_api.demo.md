# 情報漏洩デモ台本: ひかり診療所

この台本は説明者向けであり、`clinic_results_api/` の検査対象には含めない。

## 想定インシデント

患者向けアプリの利用者が通信内容から共通APIキーを知り、患者IDを順番に変えて他人の検査結果を閲覧した。その後、文書ダウンロードAPIの `path` にDBファイルの場所を指定し、患者情報と検査結果をまとめて取得した。認証のない管理用CSV出力URLも検索エンジンの巡回ログから発見され、氏名・連絡先・診断名・検査結果が外部へ流出した。

## 5分の進行

1. `TARGET_DIR=./samples/clinic_results_api bun run dev` で起動し、「患者本人だけが自分の検査結果を見るAPI」と背景を説明する。
2. 検査を開始し、最初はコード上の事実だけを見せる。特に共通APIキー、患者IDを直接SQLへ入れる箇所、任意パスのファイル送信、認証なしのCSV出力に注目する。
3. 事故シミュレーションでは、最初の兆候を「同じAPIキーから短時間に連番の患者IDへアクセス」とする。
4. 次に `documents/download` から通常の結果票ではないファイルが取得され、直後に `admin/export` が大量応答を返した、と説明する。
5. 影響範囲を「患者の基本情報と診療情報」に広げ、単なるコード品質ではなく、本人への通知、診療所の信用、系列展開の停止判断につながることを示す。
6. 修正案を適用し、少なくとも患者単位の認可、ダウンロード対象の固定ディレクトリ化、管理APIの認証、秘密情報の環境変数化が差分に現れることを確認する。

## 説明時の答え合わせ

- `patient_results` はAPIキーしか見ておらず、ログイン中の患者とURLの `patient_id` が一致するか確認していない。
- `download_document` は利用者が指定したパスをそのまま `send_file` に渡す。
- `export_patients` は認証なしで全列をCSVとして返す。
- APIキーはソースコードにあり、患者向けアプリと検査会社で共有されるため、漏れた後の追跡と個別失効が難しい。
- 患者ID・メールアドレスがログに残り、ログ閲覧者にも情報が広がる。

## デモ上の注意

架空の組織・患者データだけを使う。外部公開せず、`127.0.0.1` からアクセスする。脆弱なAPIを実際の個人情報や共有ネットワークへ接続しない。
